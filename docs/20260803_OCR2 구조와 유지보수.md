## 3. 전체 아키텍처

- 브라우저 영역
  - 사용자가 PNG 또는 PDF를 선택
  - `FileReader.readAsDataURL()`로 파일을 Base64 Data URL로 변환
  - JSON 요청 본문에 파일명, MIME 형식, Data URL을 담아 내부 API 호출
  - API가 돌려준 JSON 문자열을 파싱해 React 상태에 저장
  - 화면 수정, 목록 선택, 정렬, 조합 계산, Excel 생성은 모두 브라우저에서 수행
- 서버리스 API 영역
  - `/api/ocr`
    - 영수증 전용 프롬프트 사용
    - 날짜, 시간, 상호명, 금액, 전체 텍스트를 JSON 객체로 요청
  - `/api/read`
    - 문서 전체 읽기 프롬프트 사용
    - 원문, 정리된 본문, 교정 목록을 JSON 객체로 요청
  - 서버 환경 변수의 `OPENAI_API_KEY`로 OpenAI Responses API 호출
  - 브라우저에는 API 키를 노출하지 않음
- 외부 서비스 영역
  - `https://api.openai.com/v1/responses` 호출
  - 기본 모델은 `gpt-5-mini`
  - `OPENAI_MODEL` 환경 변수로 모델 교체 가능
- 영속성
  - 현재 없음
  - 저장 버튼은 서버나 파일에 저장하는 것이 아니라 `App.jsx`의 `savedReceipts` 배열에 추가하는 동작
  - 새로고침하거나 탭을 닫으면 저장 목록이 사라짐

## 4. 영수증 정리 기능의 동작 순서

1. 파일 선택
   - `FileUploader.jsx`에서 PNG 또는 PDF만 선택 가능
   - `App.jsx`가 선택 파일을 상태로 보관
   - `URL.createObjectURL()`로 이미지 또는 PDF 미리보기 생성
   - 컴포넌트 정리 시 `URL.revokeObjectURL()`로 URL 해제
2. OCR 실행
   - `requestOcr(file)` 호출
   - production에서는 기본적으로 `/api/ocr` 사용
   - development에서는 `VITE_OCR_API_ENDPOINT`가 비어 있으면 mock 응답 사용
3. API 요청
   - 파일을 Data URL로 변환
   - `{ fileName, mimeType, dataUrl }` JSON을 POST로 전송
   - PDF는 OpenAI 입력의 `input_file.file_data`로 전달
   - 이미지는 `input_image.image_url`로 전달
4. 모델 처리
   - 영수증에서 날짜, 시간, 상호명, 최종 금액, 전체 텍스트 추출
   - Responses API의 JSON object 출력 형식 사용
5. 클라이언트 후처리
   - 모델 응답 문자열을 우선 JSON으로 직접 파싱
   - 실패하면 첫 `{ ... }` 모양의 문자열을 정규식으로 찾아 재파싱
   - `parseReceiptText()` 결과를 보조값으로 사용
   - 날짜는 `YYYY-MM-DD`로 정규화
   - 금액 보조 파서는 원문 숫자 중 가장 큰 값을 선택
6. 사용자 검토
   - 날짜, 시간, 상호명, 금액, 전체 OCR 텍스트를 직접 수정 가능
7. 목록 저장
   - `crypto.randomUUID()`로 ID 생성
   - 파일명과 저장 시간을 추가
   - 브라우저 메모리의 배열 앞쪽에 삽입
8. 활용
   - 날짜·시간·상호명·금액 기준 정렬
   - 전체 또는 선택 항목을 Excel로 내려받기
   - 선택 항목으로 1,000,000원 조합 검색

## 6. 1,000,000원 조합 계산 원리

- 대상
  - 사용자가 체크한 영수증 중 금액이 0보다 큰 항목
- 알고리즘
  - 합계별 영수증 목록을 `Map`에 저장하는 부분합 동적 계획법
  - 초기 상태는 합계 0과 빈 배열
  - 각 영수증을 한 번씩 순회하면서 기존 합계에 현재 금액을 더함
  - 목표 금액을 초과하는 경우 저장하지 않음
  - 동일 합계가 이미 있으면 최초 조합을 유지
- 결과
  - 정확히 1,000,000원이 있으면 `exact`
  - 정확한 값이 없으면 1,000,000원 미만의 최대 합계를 `under`로 반환
- 장점
  - 가능한 합계를 직접 관리해 완전한 부분집합 나열보다 실용적
- 한계
  - 금액 단위가 1원이고 항목 수와 가능한 합계 종류가 많으면 메모리와 계산량 증가
  - 목표 금액이 코드 상수로 고정
  - 같은 합계를 만드는 여러 대안을 비교하지 않음
  - 영수증 수 최소화 등의 부가 기준 없음

  - `OPENAI_API_KEY` 같은 비밀 환경 변수는 Vercel 프로젝트 설정에 비공개로 등록되어 있음

- 코드와 Git에서 확인된 사실
  - production 프런트엔드는 `/api/ocr`와 `/api/read` 상대 경로를 호출
  - `api/*.js`는 `request`, `response`를 받는 서버리스 핸들러 형태
  - Vite 빌드는 `dist/`에 정적 파일을 생성
  - Git 원격 저장소는 `https://github.com/jin0190/OCR2.git`
  - 로컬 `v1` 브랜치의 HEAD와 `main`, 원격 추적 브랜치가 모두 커밋 `9c882b9`를 가리킴
  - GitHub Actions, Dockerfile, `vercel.json`, Netlify 설정 파일은 없음
  - `.git/hooks`에는 sample 파일만 있고 실제로 동작하는 local hook은 없음
  - `package.json`의 `build` 명령은 `vite build`뿐이며 Vercel CLI나 별도 배포 명령을 실행하지 않음
  - 2026-08-03 원격 조회 결과 `origin/main`과 `origin/v1`은 모두 커밋 `9c882b9`를 가리킴
- 자동 배포가 일어나는 지점
  - 이 폴더에서 `npm run build`만 실행하면 로컬 `dist/`가 갱신될 뿐 Vercel 배포는 발생하지 않음
  - Vercel Git Integration이 GitHub 저장소에 연결되어 있으면 연결 브랜치로 push할 때 Vercel이 원격 커밋을 감지해 자체 환경에서 install과 build를 실행하고 배포함
  - production branch가 `main`이면 `git push origin main`이 production 배포를 유발하는 일반적인 구성
  - `v1`이 production branch로 지정되어 있다면 `git push origin v1`이 production 배포를 유발함
  - 어느 브랜치가 production으로 설정됐는지는 로컬 Git 정보만으로 확정할 수 없으므로 Vercel의 Project Settings → Git → Production Branch에서 확인 필요
  - production branch가 아닌 연결 브랜치 push는 보통 Preview Deployment를 생성
- 현재 Git 관계
  - 현재 체크아웃 브랜치: `v1`
  - `v1`은 `origin/v1`을 추적
  - 로컬 `main`은 `origin/main`을 추적
  - 로컬과 원격의 `main`, `v1`은 현재 동일한 커밋
  - 새 문서는 아직 Git에 추가·커밋·push되지 않은 `docs/` 변경
  - 기존 `.env.example` 삭제도 커밋되지 않은 상태
  - 따라서 지금 `npm run build`를 다시 실행해도 자동 배포되지 않으며, 변경을 선별해 commit한 후 올바른 원격 브랜치로 push해야 Vercel 자동 배포가 시작됨
- 앞으로의 브랜치 운영 원칙
  - `main`: Vercel production 자동 배포 브랜치
  - `v1`: production 장애 시 돌아갈 수 있는 안정 버전 포인터
  - 새 기능은 검증 후 `main`에 반영하고 push해 자동 배포
  - 배포가 안정적임을 확인하기 전에는 `v1`을 새 커밋으로 이동하지 않음
  - 새 버전을 안정 버전으로 확정할 때만 별도 태그를 만들고 `v1`을 해당 커밋으로 이동
  - 단순히 `v1`을 항상 `main`과 동시에 push하면 롤백 기준점 역할을 잃으므로 두 브랜치를 의도적으로 분리
- 여전히 로컬에서 확인할 수 없는 사항
  - 실제 서비스 URL
  - 자동 배포 브랜치와 배포 성공 여부
- 권장 Vercel 배포 설정
  - Build Command: `npm run build`
  - Output Directory: `dist`
  - Install Command: `npm install` 또는 CI에서는 `npm ci`
  - 환경 변수: `OPENAI_API_KEY`, 필요 시 `OPENAI_MODEL`
  - `VITE_OCR_API_ENDPOINT`, `VITE_FULL_READ_API_ENDPOINT`는 같은 배포의 `/api`를 쓸 때 비워도 됨
- 배포 후 점검

## 13. 위험 요소 및 기술 부채

### 높은 우선순위

- 데이터 유실
  - 저장 목록이 React 메모리에만 존재
  - 새로고침 즉시 전체 목록 소실
  - 최소한 IndexedDB 또는 서버 DB 도입 필요
- 업로드 검증 부족
  - 브라우저 `accept` 속성만 있고 서버에서 MIME, 확장자, 파일 크기를 검증하지 않음
  - 임의 요청으로 큰 payload나 예상하지 않은 형식 전달 가능
- Base64 JSON 전송
  - 원본보다 약 33% 커지고 JSON 오버헤드가 추가됨
  - 큰 PDF는 서버리스 요청 본문 제한, 메모리 제한, timeout에 걸릴 가능성이 큼
  - 업로드 저장소 또는 OpenAI Files API를 활용하는 구조 검토 필요
- 인증과 호출 제한 없음
  - 공개 배포 시 누구나 endpoint를 호출해 OpenAI 비용을 발생시킬 수 있음
  - 인증, rate limit, 일일 한도, origin 검증, 사용량 기록 필요
- 오류 정보 전달
  - OpenAI 오류 응답 전체를 클라이언트에 전달할 수 있음
  - 사용자용 오류 코드와 서버 로그를 분리하는 것이 좋음

### 중간 우선순위

- 테스트 부재
  - 조합 알고리즘, 영수증 파서, API 응답 파서에 자동 테스트가 없음
  - 변경 후 회귀 여부를 사람이 직접 확인해야 함
- 응답 파싱 취약성
  - `/\{[\s\S]*\}/` 정규식은 여러 JSON 객체나 불완전 응답에서 과도하게 매칭할 수 있음
  - 서버에서 구조 검증 후 완성된 JSON만 클라이언트에 반환하는 편이 안전
- 데이터 스키마 검증 없음
  - 날짜, 시간, 금액, corrections 항목 타입을 런타임에서 엄격히 검증하지 않음
  - Zod 등의 스키마 검증 도입 권장
- 중복 코드
  - 두 API의 검증, OpenAI 호출, 파일 입력 생성, 결과 텍스트 추출이 거의 동일
  - 두 클라이언트의 Data URL 변환과 JSON 추출도 중복
  - 공통 모듈화 시 수정 누락 위험 감소
- 개발 환경과 production 차이
  - 로컬에서는 mock, production에서는 실제 API가 기본이므로 실제 연동 오류를 늦게 발견할 수 있음
  - 통합 개발 명령 또는 staging 환경 필요
- 의존성 선언
  - `package.json`이 모든 패키지에 `latest`를 사용
  - lock 파일이 있더라도 새로 의존성을 갱신할 때 예상치 못한 major update가 들어올 수 있음
  - 검증된 major/minor 범위로 명시 권장

### 낮은 우선순위

- 번들 크기
  - 단일 JavaScript chunk가 500 kB를 넘어 빌드 경고 발생
  - `xlsx`를 Excel 버튼 사용 시 동적 import하도록 분리 가능
- 접근성
  - 체크박스에 명시적인 접근성 이름이 없음
  - 파일 처리 결과에 `aria-live` 영역이 없음
  - 복사 완료 피드백이 없음
- 사용자 경험
  - 저장 성공 여부 표시가 없음
  - 동일 영수증 중복 저장 방지 없음
  - 업로드 제한 크기 안내 없음
  - 요청 취소 기능 없음
  - 탭 이동 시 정리 화면 상태가 유지되지만 새로고침 시에는 소실
- Excel
  - 열 너비, 통화 서식, 필터, 헤더 고정이 설정되지 않음

## 18. 앞으로의 OCR 작업 흐름 개선안

### 목표 작업 방식

- 현재 방식
  - 이미지 한 장 선택
  - OCR 실행
  - 금액 확인 및 수정
  - 목록 저장
  - 다음 이미지를 다시 선택해 같은 과정 반복
- 개선 목표
  - 여러 파일을 한 번에 선택
  - 파일별 OCR을 순차 또는 제한된 병렬 방식으로 자동 실행
  - 파일마다 추출 금액과 신뢰 상태를 한 화면에서 검토
  - 정상 항목은 일괄 목록 추가
  - 애매한 항목만 개별 수정
  - 처리 도중 실패한 파일만 재시도

### 지원할 이미지 확장자

- 우선 지원 권장
  - `.png`: 현재 지원
  - `.jpg`, `.jpeg`: 영수증 사진에서 가장 일반적
  - `.webp`: 모바일·웹 저장 이미지 대응
  - `.pdf`: 현재 지원 유지
- 선택 지원
  - `.heic`, `.heif`: iPhone 원본 사진 대응
  - 브라우저 미리보기와 OpenAI 입력 호환성을 단순화하려면 클라이언트 또는 서버에서 JPEG로 변환 후 처리
  - 변환 시 EXIF 방향 보정과 해상도 유지 필요
- 낮은 우선순위
  - `.bmp`, `.tiff`, `.tif`
  - 파일 크기가 크고 브라우저·API 호환 처리가 추가로 필요하므로 실제 사용자 파일이 있을 때 도입
- 업로더 변경 방향
  - `<input multiple>` 사용
  - `accept="image/png,image/jpeg,image/webp,image/heic,image/heif,application/pdf"` 형태로 확대
  - 확장자뿐 아니라 서버에서 MIME, magic bytes, 파일 크기 검증

### 여러 이미지를 한 번에 처리할 수 있는가

- 가능
  - 가장 안정적인 방식은 여러 파일을 선택하되 파일마다 `/api/ocr` 요청을 하나씩 보내는 구조
  - 결과도 파일별로 독립 관리하므로 한 파일 실패가 전체 작업을 망치지 않음
- 한 요청에 여러 이미지를 모두 넣는 방식은 초기 구현에서 비권장
  - 응답에서 어느 결과가 어느 파일인지 잘못 대응될 수 있음
  - 요청 크기와 처리 시간이 급격히 커짐
  - 한 파일 오류로 전체 batch가 실패할 수 있음
  - 재시도 시 이미 성공한 파일까지 다시 과금될 수 있음
- 권장 동시 처리 수
  - 초기값 2개
  - 운영 중 rate limit, 평균 파일 크기, Vercel 실행 시간, OpenAI 응답 속도를 확인한 뒤 3개까지 조정
  - `Promise.all()`로 파일 수 전체를 무제한 병렬 처리하지 않음
- 파일별 상태 모델 권장
  - `queued`: 처리 대기
  - `processing`: OCR 진행 중
  - `review`: OCR 완료, 사용자 확인 필요
  - `approved`: 목록 추가 승인
  - `failed`: 처리 실패, 재시도 가능

### 권장 화면 구조

- 상단 업로드 영역
  - 드래그 앤 드롭
  - 여러 파일 선택
  - 총 파일 수와 총 용량 표시
  - 중복 파일 경고
- 처리 대기열
  - 작은 미리보기
  - 파일명
  - 처리 상태
  - 날짜, 상호명, 금액
  - 오류 또는 검토 필요 표시
- 검토 방식
  - 확실한 행은 체크된 상태로 표시
  - 금액이 0이거나 날짜·상호명이 비어 있으면 `검토 필요`
  - 행을 누르면 오른쪽 패널에서 큰 이미지와 전체 OCR 텍스트, 수정 필드 표시
  - 키보드로 다음 항목 이동 및 승인 가능
- 일괄 작업
  - `선택 항목 목록에 추가`
  - `정상 항목 모두 승인`
  - `실패 항목 재시도`
  - `처리 완료 항목 Excel 다운로드`

## 19. 최종 판단

- 현재 프로젝트는 작은 규모의 OCR 업무 도구로서 기능 흐름이 단순하고 빠르게 이해되는 편
